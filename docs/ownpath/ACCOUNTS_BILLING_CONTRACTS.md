# Accounts/billing frozen browser contract v1

Frozen 16 October 2026 for AB-00. Interface freeze is not evidence that endpoints or provider configuration are implemented. Canonical exports: `src/lib/accounts-billing/contracts.ts`; dependency-free request parsing and domain restore boundary: `contracts.validation.ts` (imports existing local Translator domain only). No changes to core types. Backend writer owns these modules; FE consumers import DTOs with `import type`. Changes require coordinated version/review, not unilateral FE assumptions.

## Transport and trust

Same-origin JSON APIs; browser uses `credentials: 'same-origin'`. All identity, billing and saved-session responses, including errors, use `Cache-Control: no-store`. Every browser mutation requires exact configured Origin validation and an HttpOnly-cookie double-submit CSRF token in `X-CSRF-Token`. `GET /api/auth/csrf` returns `{csrfToken}` and establishes the cookie binding; token is not an auth credential, is no-store and cannot be supplied by a cross-origin caller. Refuse unconfigured origins, cross-origin requests and missing/mismatched bindings. This local implementation combines explicit Origin checks with constant-time token comparison; it is not a server-stored synchronizer session or a reviewed multi-subdomain deployment policy. Do not rely on SameSite alone. No wildcard credentialed CORS. The webhook is the sole mutation exception, using provider signature instead. CSRF token creation must precede login cookie exchange too.

JSON-only browser mutations reject unknown fields, non-object roots and oversized streaming bodies *before* decoding. Auth body cap 16 KiB; other ordinary mutations 4 KiB; snapshot mutations 144 KiB with independently enforced 128 KiB UTF-8 serialized snapshot cap. Validators accept already decoded bounded JSON; they do not implement transport, authorization, token verification or rate limiting. Signed webhook has a separate backend raw-body cap/policy. IDs are canonical UUID v4; session IDs are server-generated UUID v4, never client-chosen. ISO dates are UTC server timestamps. `amount` means integer currency minor units, never floating-point USD. `version` and `revision` are positive monotonic server integers (entitlement version may start at zero before a projection exists).

All errors: `{error:{code,message,retryable,requestId}}` (`ApiError`); messages must be safe, not provider exceptions or input echoes. Codes: 401 `UNAUTHENTICATED`, `SESSION_EXPIRED`; 403 `RECENT_AUTH_REQUIRED`, `EMAIL_VERIFICATION_REQUIRED`, `FORBIDDEN`, `CSRF_INVALID`, `PRO_REQUIRED`; 404 `NOT_FOUND`; 409 `REVISION_CONFLICT`, `OPERATION_CONFLICT`, `OPERATION_PENDING`, `QUOTA_EXCEEDED`, `ALREADY_SUBSCRIBED`; 413 `PAYLOAD_TOO_LARGE`; 422 `INVALID_REQUEST`, `UNSUPPORTED_SCHEMA`; 429 `RATE_LIMITED`; 503 `BILLING_UNAVAILABLE`, `SERVICE_UNAVAILABLE`. `retryable` indicates same logical operation may recover, not permission to auto-repeat payment/navigation. 429 uses `Retry-After`; transient 503 may use it. Never log ID tokens, cookies, passwords or project/JD contents.

## Exact endpoints

All success bodies are the named exported DTO, without an additional data wrapper. Authentication abbreviations: **S** = verified, non-revoked Firebase cookie/project/active user; **V** = S plus provider-derived verified email. Guest catalog/CSRF have no S requirement. No browser UID/tier/customer/price/amount determines authorization or charge.

| Method and path | Auth | Request | Success |
|---|---|---|---|
| GET `/api/auth/csrf` | guest | none | 200 `CsrfResponse` |
| POST `/api/auth/session` | recent Firebase ID token | `SessionExchangeRequest` | 200 `SessionExchangeResponse`, bounded HttpOnly cookie |
| DELETE `/api/auth/session` | current: tolerate missing/expired cookie; all: S + recent auth | `LogoutRequest` | 200 `LogoutResponse`, clear cookie |
| GET `/api/account` | S | none | 200 `AccountResponse` |
| PATCH `/api/account` | V | `AccountPatchRequest` | 200 `AccountResponse` |
| GET `/api/billing/plans` | guest | none | 200 `CatalogResponse` (unconfigured is `pro.availability:'unavailable'`) |
| GET `/api/billing/status` | S | none | 200 `BillingStatusResponse` |
| POST `/api/billing/checkout` | V | `CheckoutRequest` | 200 `CheckoutResponse` |
| POST `/api/billing/portal` | V | `PortalRequest` | 200 `PortalResponse` |
| POST `/api/webhooks/stripe` | signature, expected test account/mode | raw unchanged provider body, `Stripe-Signature` | 200 `{received:true}` only after durable receipt/processing; invalid signature 400, transient receipt failure 503 |
| GET `/api/sessions` | V, no Pro required | query `cursor?`, `limit?` | 200 `SessionListResponse` |
| POST `/api/sessions` | V + current Pro | `SaveSessionRequest` | 201 `SavedSessionResponse` (replay also 201) |
| GET `/api/sessions/[id]` | V, no Pro required | UUID path | 200 `SavedSessionResponse` |
| PATCH `/api/sessions/[id]` | V + current Pro | `UpdateSessionRequest` | 200 `SavedSessionResponse` |
| DELETE `/api/sessions/[id]` | V, no Pro required | `DeleteSessionRequest` JSON body | 200 `DeleteSessionResponse` |

Webhook errors are provider-facing, not browser error DTOs; signature failures must not disclose signing details. No other custom password endpoint, saved-work alias or retired API is authorized. GET list parses only `cursor`/`limit`, rejects duplicates/unknown query keys; transport converts a decimal limit string to an integer before `parseSessionList`. Default 20, range 1–50. Cursor is opaque and bounded 2048 characters; backend must bind cursor/query to verified UID, reject tampering, paginate stable `(updatedAt,id)` descending order. Responses never return another owner's data; cross-owner access is 404, not 403.

## Auth/account consumption

Firebase official client SDK handles signup/login, configured password validation, verification, password reset and action-code links. Password/confirmation never enter these APIs, URLs or application storage. Runtime adapter: `src/lib/accounts-billing/client-auth.ts`, `createAccountsAuthAdapter(options: FirebaseOptions, emulatorUrl: string): Promise<AccountsAuthAdapter>`. It currently accepts only explicit `demo-` projects and HTTP loopback emulators. Supply reviewed sanitized public configuration; no automatic cloud fallback. FE1 must use this adapter, not invent parallel auth logic.

Frozen adapter interface: `register({email,password})` returns `{session:SessionExchangeResponse,verificationEmail:'sent'|'pending'}`; `login(credentials)` and `refreshVerification(credentials)` return `SessionExchangeResponse`; `resendVerification(credentials)` returns `{verificationEmail:'sent'|'already_verified'}`. Verification refresh/resend deliberately reauthenticate with credentials, then clear the memory-only client identity. `requestPasswordReset(email)` returns neutral `{requested:true}`; `checkAction(code)` returns `{operation}`; `applyVerification(code)` permits only VERIFY_EMAIL; `checkPasswordReset(code)` returns `{valid:true}` without exposing an email; `completePasswordReset(code,newPassword)` completes through SDK; `passwordPolicy(password)` delegates official SDK validation; `logout(scope='current')` clears server cookie then client credentials. SDK credential use is serialized across instances sharing an Auth object. No adapter stores passwords in app storage. UI owns confirmation matching/accessibility and must not log method arguments.

`AccountAuthError` exposes safe `code` (`INVALID_CREDENTIALS`, `INVALID_ACTION`, `WEAK_PASSWORD`, `RATE_LIMITED`, `UNAVAILABLE`, `REQUEST_FAILED`), `phase` (`identity`, `identity_created_session_pending`, `session`) and optional safe `apiError`. Registration that created an identity but could not exchange its server session reports `identity_created_session_pending`; do not repeat account creation or delete the identity. `accountsRequest<T>(path,method='GET',body?)` is the same-origin frozen-endpoint transport and automatically obtains the CSRF binding for mutations; supports `/api/sessions?limit=...&cursor=...`. API failures become `AccountAuthError` with `apiError`, not raw provider messages. Network errors must still be caught by UI. Do not use this helper to send passwords.

Session exchange requires recent auth (backend policy: five minutes maximum `auth_time` age), verified expected project/token, origin/CSRF and bounded cookie duration. Unverified users get account/verification access, not privileged actions. Server bootstrap is UID-idempotent; partial profile failure may return `setup:'profile_pending'`, `profile:null`, so FE must not call registration failed after the identity exists. A hard exchange failure returns safe 503; signing in and repeating exchange repairs bootstrap without deleting identity. Email/send failure is a separate SDK outcome, never implied by server setup status. On verification refresh provider identity and ID token, then exchange a new server session before enabling verified actions. Clear Firebase client credential persistence after cookie issuance using memory-only persistence; do not treat the client SDK state as app session authority.

Logout `scope:'current'` clears only this device cookie, remains idempotent if already signed out and does not claim Firebase global revocation. `scope:'all'` explicitly requests provider refresh-token/session revocation and requires recent authentication; if stale, reauthenticate through the SDK and exchange first. Neither logout scope accepts UID. Profile can edit only trimmed display name (0–80 characters); identity email/verification and plan are server-derived. Safe `next` validation is a backend/helper requirement: local approved app paths only, reject schemes, protocol-relative URLs, encoded bypasses/backslashes; fallback `/account`, never `/assessment`.

## Catalog, entitlement and hosted payments

Catalog is always `environment:'sandbox'`. Missing config is an unavailable union, never invented USD5 success. Available Pro amount is the allowed configured test Stripe Price's integer minor-unit amount, currency `usd`, interval `month`; reject live config, trials, discounts and additional tiers for this slice. Free has no checkout. `Entitlement` capabilities are authoritative for UI display but server recomputes authorization at write time, including paid-through expiry and email verification. No local generation paywall.

`BillingStatusResponse.subscription` is sanitized lifecycle state; `blocked` covers refund/dispute or unsupported provider states conservatively. Pro requires reconciled allowed active/paid state and nonexpired paid-through. Pending/incomplete/past_due/unpaid/paused/canceled/expired/blocked do not grant new writes; cancellation-at-period-end retains Pro only until verified paid-through. Reconciliation pending/unavailable is not a new grant. `canManageBilling` indicates a trusted owned customer exists; no customer/subscription IDs are exposed. `asOf` is server reconciliation time, not proof it is safe to ignore expiry. Checkout/portal return only HTTPS provider URLs validated by backend approved host policy; no browser return URL. Server return routes: `/checkout/return`, `/checkout/cancel`; portal return `/account/billing`. Frontend routes consume no `success` flag as entitlement.

## Operations, revisions and quota

`operationId` is a UUID v4 from `crypto.randomUUID()` created once per explicit logical action, retained for retries including lost responses. Same UID/action/path/key and normalized payload returns the original result; same scope/key with different payload returns `OPERATION_CONFLICT`. Never generate a new key merely because of timeout. Scope includes verified UID; keys never choose ownership. Backend persists dedupe records for at least 24 hours (document exact policy before deployment), including delete tombstone results; expired keys cannot authorize stale revisions. Pending side effects return `OPERATION_PENDING` with retry guidance; no fake success. Checkout additionally enforces one live/pending subscription per UID/environment *across different keys* using durable reservation/recovery and stable provider idempotency keys. Portal keys dedupe its provider call, not entitlement.

Create has no supplied session ID/revision; returns server ID/revision 1. Update is a full title/snapshot replacement with positive `expectedRevision`, increments revision exactly once. No partial merge or silent last-write-wins. Delete also requires expected revision; matching previously successful operation replay succeeds even after deletion. Different key on missing resource returns 404. Both update/delete compare revision atomically; dedupe of matching successful operation is checked before stale revision comparison, with identity/verification still rechecked. New/update writes require current Pro even if retrying; downgrade cannot create another write. Quota defaults 50; server can lower configured limit and returns actual quota/capability limit. Atomically enforce quota, insert/update/revision, dedupe and delete decrement. Owner read/delete survives downgrade. No external provider calls inside retryable Firestore transactions.

## Saved snapshot and restore: review gate, not core hydration

`SavedSnapshotV1` contains version 1, intake, four allowlisted optional interview answers, complete derived PreparedSession (sources/facts/requirements/questions) and historical ReviewedBullet candidates. It is not a trusted PreparedSession just because it came from Firestore. `parseSnapshot` reruns current `prepareSession`/`confirmFacts`, compares the entire derived tree including source spans and IDs, rejects unknown/oversized fields, duplicate candidate IDs and invalid references. Historical confirmations may be stored; arbitrary historical accepted/edited flags and generated text **do not establish truth**. Browser can submit deceptive wording even in a schema-valid snapshot. Wording remains private untrusted user content, rendered as text, never HTML or instructions. Candidates cap 50; each wording 500 characters. Current supported domain inputs/answer bounds still apply. If a future domain change invalidates an old derived snapshot, fail recoverably; do not silently reinterpret it or delete it. Future migration needs separately reviewed schema/version support.

**Mandatory FE2 restore boundary:** call `restoreSnapshot(unknown)` (including on API-fetched snapshots) rather than assigning stored `prepared`/`candidates` to UI state. It validates again, rebuilds prepared state with **all facts unconfirmed**, and emits `wordingDrafts` with only ID/current wording/historical generated text plus literal `provenance:'untrusted_saved_wording'`. It emits no accepted/rejected flags or core candidate objects. `reviewRequired:true` is invariant, including for unedited/server-saved snapshots. No export/clipboard acceptance may survive restore. Never pass historical generated text through core template/provenance authority.

FE2 must show restored wording separately as untrusted drafts, require renewed source/fact confirmation, regenerate through existing domain boundary, then require explicit wording review. Do not merge drafts by ID into fresh candidates automatically: IDs do not prove grounding. To reapply draft wording, use an explicit edit action after fact review, preserve edited provenance and existing edited-claim warnings, reset acceptance; explicit acceptance remains required. Detached drafts have no fact/requirement grounding until this workflow. Restore itself never autosaves or upgrades tier. This adapter/UI policy requires FE2 + backend/domain read-only review before connection; runtime validation tests alone are not UI acceptance evidence.

## Current backend implementation gates (not target-contract changes)

The backend continuation adds `admin.ts`, `server-config.ts`, `server-errors.ts`, `server-security.ts`, `server-identity.ts`, `server-rate-limit.ts`, `server-sessions.ts`, `server-billing.ts`, `server-api.ts`, `client-auth.ts` and explicit route modules for the paths above. Only `disabled` and strict loopback `emulator` accounts modes are accepted; no cloud/deployed mode is implemented. Admin uses an ephemeral generated inert certificate (required by installed Admin Firestore adapter), not a cloud-owned key, ambient ADC or cloud metadata discovery; the guarded Auth emulator SDK itself uses its owner token. Session-cookie issuance, profile recovery and owned read/delete/history are implemented; cookie duration defaults five days, bound five minutes–fourteen days. Global Auth exchange limit 300/minute plus UID exchange 20/minute, CSRF 600/minute, authenticated account operations 120/minute/UID, global revoke 10/minute/UID. Counters are shared Firestore transactions; these are conservative local controls, not a validated deployed abuse policy or a substitute for Firebase provider controls.

**Billing activation is opt-in and default-off.** The durable lifecycle implementation replaces the historical constant-false stub; it requires `OWNPATH_SANDBOX_BILLING_ENABLED=true` plus all four validated server-only Stripe test settings. With the gate off or settings missing, catalog/checkout remain unavailable and no Pro authority is installed. This is an operational gate change, not a browser DTO change. Only demo loopback account mode is supported. An operator must separately complete the real sandbox matrix before claiming external acceptance; no actual Stripe sandbox execution has occurred.

When explicitly enabled/configured, the real Stripe23 adapter validates test account/product/Price, creates owned hosted checkout/portal sessions and verifies raw signatures. Firestore persists customer/checkout reservations and signed-event receipts; failed reconciliation remains pending and returns503 for provider retry, completed durable processing returns success. Canonical paid invoice/payment/charge authority, binding, generation/fencing, freshness and paid-through expiry control Pro writes; redirects and completion alone grant nothing. Matching completed-checkout reservations are retired only after canonical subscription evidence accounts for them, allowing a fresh operation after cancellation while old operations remain non-reusable. Refund/dispute history blocks new Pro writes/checkout conservatively. Existing verified-owner reads/deletes survive downgrade; all quota responses use the same configured server limit. `BillingService.retryPending` is an internal bounded operator entry, not a provisioned scheduler. Full deployed worker/monitoring/retention and cloud setup remain open.

Operational saved-session dedupe stores original summary/hash (including title), **not snapshot/project/JD copies**; a hash-matched retry supplies its original snapshot to reconstruct the response. Metadata can survive snapshot deletion. Operation authorization expiry is 24 hours and cursor expiry 30 minutes, checked by code; physical TTL/retention cleanup is a separate integration/deployment responsibility, not a running worker claim. A retry after the dedupe window is a new create, so UI must not silently replay old abandoned create keys indefinitely. No cloud IAM, backup/recovery, actual email delivery, shared-shell auth cutover, frontend restore integration or production readiness is implied by these modules.
