## Application configuration

Accounts default to disabled. Use only explicit loopback emulator mode for synthetic local development, standard Auth/Firestore emulator host variables, a `demo-ownpath-*` project, and the trusted application origin. See the contracts/backend configuration for the exact client adapter settings. Never set cloud Admin credentials in the test harness. Private account/billing/session responses are no-store. Existing Supabase runtime consumers remain staged and isolated pending reviewed frontend removal; do not deploy this partial candidate.

`OWNPATH_SAVED_SESSION_LIMIT` defaults to50 and accepts integers1–50; the same server policy supplies account capabilities and history/write quota. Billing requires explicit `OWNPATH_SANDBOX_BILLING_ENABLED=true` (default false) and all four server-only `STRIPE_*` settings in `.env.example`. Only `sk_test_` keys, the configured account and an active monthly USD recurring Price/product are accepted. Missing configuration or disabled gate leaves checkout unavailable. The demo harness deliberately strips these settings: billing integration cases use actual Firestore with a deterministic fake provider, never Stripe network calls. Real-adapter SDK-response fixtures are also deterministic, not network acceptance. The sandbox adapter bounds each enumerated provider list to1,000 objects and fails closed beyond that size; broader account-scale provisioning/recovery needs separate review.

### Sandbox reconciliation and recovery policy

Webhooks verify raw-body signatures and configured account membership, persist minimal deduplicated receipts, invalidate stale entitlements and reconcile canonical provider state synchronously. A processing failure leaves a durable pending receipt and returns503 so Stripe retries; a completed receipt returns success. Status requests can reconcile pending/stale customer projections. `BillingService.retryPending(limit)` is an explicit internal/operator entry for bounded pending-event recovery; no deployed scheduler or worker is provisioned. The committed billing-event index supports this query. Operator automation, monitoring and retention remain deployment gates.

Pro requires an allowed active subscription plus a verified successful full-amount paid invoice/charge, matching customer, product, Price and bounded paid-through period. Projection freshness is at most five minutes, and expiry is checked on every saved-session write. Past-due/unpaid/incomplete/paused/trial/unknown-price states deny new writes. Refund/dispute history blocks Pro and new checkout conservatively until a separately reviewed recovery policy; data remains owner-readable/deletable. Customer/checkout logical reservations and provider keys survive lost responses; uncertain operations older than23 hours fail pending rather than risking a second charge/subscription. Resolve those against provider records before any manual repair; never erase reservations to force a retry.
